# 项目问题汇总（面试版）

这份材料用于面试复盘。表述原则是：说明问题、分析原因、讲出采取的工程措施和验证方式，同时明确当前边界。不要把“计划实现”说成“已经上线”。

## 1. 如何把一个课程式 Qt 人脸识别示例变成可维护的工程基线？

**问题**：原项目能展示人脸识别，但依赖硬编码、数据访问和线程边界都偏演示性质，换机或长期运行风险较高。

**做法**：先固定 Qt 5.12 + MinGW 7.3 与现有 OpenCV 4.5.2、SeetaFace2 的可构建组合，避免一开始同时做 Qt6、CMake、算法库替换三件高风险事情。随后抽出应用配置模块、私有数据目录和本地依赖配置文件，把“能跑”变成“可重复构建、可解释运行”。

**验证**：Release 构建成功，开发环境启动成功，打包后在独立目录启动成功。

**边界**：尚未迁移 Qt6/CMake；这是刻意延后而非遗漏，避免升级期间失去可运行基线。

## 2. 为什么要把模型、数据库和阈值从代码中拿出来？

**问题**：硬编码模型路径使程序只能在开发机运行；数据库和照片散落在工作目录，也不利于发布和清理。

**做法**：设计 `AppConfig`，通过环境变量配置模型目录、数据目录、相似度阈值和考勤冷却时间。默认数据落到 Windows 用户应用目录，启动时验证三个人脸模型文件是否齐全。

**价值**：部署差异被收敛到配置层，模型缺失可诊断，业务参数可在不改代码的前提下调优。

**追问准备**：生产版本可进一步改为 INI/JSON 设置页，并增加配置校验、版本号和迁移策略。

## 3. 人脸相似度最高为什么不能直接判定为本人？

**问题**：特征检索一定会返回最高分，即使画面中是完全未登记人员；直接取第一名会产生误签到。

**做法**：把“候选排序”和“身份确认”分离，引入可配置相似度阈值，默认值为 0.70；低于阈值归为未知人员，不进入考勤写入逻辑。

**价值**：业务决策不再完全依赖算法返回顺序，能通过样本集对误识率和漏识率做权衡。

**边界**：0.70 是当前默认值，不是经过完整 ROC 曲线标定得到的最终生产阈值。

## 4. 如何处理连续帧导致的重复考勤？

**问题**：视频输入在 30 FPS 下持续识别，同一人停留数秒就可能写入数十条记录。

**做法**：采用三层控制。第一层是 `AttendanceStateMachine`：同一工号连续 `N` 帧达到阈值才确认，默认 3 帧；人脸消失、变成未知人或切换来源都会清零。第二层是按人员的 30 秒冷却，避免重复触发。第三层是 SQLite 的 `event_key` 唯一索引和事务，即使进程重复提交也只能保留一个业务事件。当天状态机控制“未签到先签到、已签到后才允许签退、当天完成后抑制后续事件”。

**价值**：从“每帧一次识别结果”过渡到“每个有效业务事件一次写入”。

**边界**：内存 SQLite 已覆盖确认、签到、签退与幂等；真实环境下的阈值和长时间稳定性仍需用更多采集样本标定。

## 5. 为什么使用参数化 SQL 和事务？

**问题**：注册信息和考勤记录如果使用字符串拼接 SQL，会受引号等输入影响，也会有注入风险；多步骤写入失败可能留下半条数据。

**做法**：将核心写入改为预编译语句和绑定参数，使用 SQLite 事务包裹相关写入，并统一修复考勤时间字段为 `checktime`。

**价值**：提高输入健壮性和数据一致性，使失败能够回滚并被上层处理。

**追问准备**：后续会针对人员编号、日期和事件类型补充唯一索引或幂等表，而不是只依赖内存冷却。

## 6. Qt UI 与 OpenCV 识别线程之间最大的风险是什么？

**问题**：采集线程不断复用图像缓冲区，识别线程异步处理同一 `cv::Mat` 时可能读到下一帧或失效内存；关闭窗口时还有后台线程访问已析构对象的风险。

**做法**：向识别工作线程提交克隆后的图像，明确跨线程帧所有权；关闭时等待工作线程结束。

**价值**：优先消除偶现花屏、识别结果错位和退出崩溃等难复现问题。

**追问准备**：RTSP 接入后会增加有界队列和丢帧策略，控制积压延迟而不是无限缓存。

## 7. 为什么当前不让 Qt 直接访问摄像头？

**问题**：UVC 摄像头和麦克风物理连接在 RK3568，且网关正在使用它们进行采集、音视频处理和 RKNN 推理。

**做法**：把系统拆为媒体数据面和业务控制面：RK3568 网关独占设备、编码和上游媒体处理；Qt 客户端只从未来验收的 RTSP URL 读取视频，在 Windows PC 完成人脸识别与考勤。

**价值**：避免双进程抢占设备、重复推理和端口冲突，也让两个项目的技术重点清晰可区分。

**边界**：当前网关尚未正式输出 RTSP，所以 Qt 暂以本地视频文件作为开发和回归输入。

## 8. RTSP 客户端会如何设计断流和“无人脸”两类状态？

**问题**：网络断开、服务端停止和画面中无人脸都可能导致没有考勤事件，但处理方式完全不同。

**做法**：已实现 `IVideoSource` 抽象，并完成 `VideoFileSource`、`LocalCameraSource` 和 `RtspSource` 的基础结构。RTSP 状态设计为连接中、播放中、输入中断、重连等待和失败；断流期间停止投递识别和考勤事件。画面正常但无人脸时仍属于播放中，只清空连续确认进度并显示未检测到人脸。

**价值**：避免把基础设施故障伪装成算法识别结果，并为日志、监控和自动重连提供清晰边界。

**边界**：`RtspSource` 目前只完成 URL 校验、状态文本和非法地址测试；没有连接任何真实 RTSP 地址，也没有对 RK3568 做端到端验证。

## 9. 如何解决 Windows 上 Qt 应用“开发机能跑、拷走就打不开”的问题？

**问题**：Qt、MinGW、OpenCV、SeetaFace、SQLite 插件和模型均是运行依赖，只复制 exe 会缺 DLL 或插件。

**做法**：编写显式打包脚本，复制 Qt 核心 DLL、MinGW 运行库、`qwindows.dll`、`qsqlite.dll`、OpenCV/SeetaFace DLL 和三个模型文件；在独立发布目录做启动测试。

**价值**：发布依赖由脚本固定，减少手工漏拷贝，便于后续形成可复现的交付物。

**边界**：依赖清单绑定当前 Qt5/MinGW 与 SDK 版本，升级依赖后需重新做干净环境验证。

## 10. 两个都与视觉有关的项目，怎样避免简历同质化？

**问题**：如果 Qt 项目也在板端做采集、编码、推理，会和 RK3568 音视频网关重复，简历难以说明自己的系统分层能力。

**做法**：网关项目重点讲 V4L2/ALSA、MJPEG、RKNN、时间戳、队列、媒体输出和长稳；Qt 项目重点讲 RTSP 消费、PC 侧识别、线程模型、业务状态机、SQLite 事务和发布交付。通过明确的只读接口把两者串成一个边缘到桌面的完整系统。

**价值**：形成“边缘媒体数据面 + 桌面业务控制面”的互补项目组合，而不是两个相同的人脸识别 Demo。

**边界**：严禁为了 Qt 演示而操作网关硬件、NPU、端口、配置、文件或服务。

## 11. 项目当前的可量化验证有哪些？

**已完成**：Qt5 Release 成功构建；8 项自动化测试通过；开发环境与独立打包目录均可启动。本机摄像头连续运行 `1800.342` 秒，共读取 `38380` 帧，平均 `21.318 FPS`；识别请求/返回 `379/379`，平均延迟 `13.549 ms`、最大 `32 ms`；CPU 平均 `1.252%`、最大 `1.696%`，工作集 `188.250-202.930 MB`，运行中没有源错误。内存 SQLite 测试覆盖三帧确认、签到、自动/手动签退、三秒边界、人员变化、无人脸、停止视频、未签到和幂等；用户已完成对应真人 UI 回归。Excel 正确解码 UTF-8 BOM CSV；Windows 便携包在移除开发 PATH 后启动成功，且隐私文件审计与 SQLite 审计通过。

**待补充**：摄像头此前黑流的确定根因与再次掉线后的真实重连恢复数据；从未安装 Qt/OpenCV/SeetaFace 的干净 Windows 机器启动证据；断流恢复时延、RTSP 端到端时延和资源占用。最后三项不能用本机短测代替。

**面试建议**：只报已经测得的数据；未测数据表述为“下一轮验收指标”，不要虚构 FPS、准确率或时延。

## 12. 一分钟项目介绍模板

“我把一个 Qt5/OpenCV/SeetaFace 的考勤示例整理成可构建、可配置和可发布的 Windows 人脸考勤控制台。工程上，我用 `IVideoSource` 解耦本地视频和 Windows 本机摄像头输入，用 Qt 信号槽隔离 UI、帧采集和识别任务；识别成功后通过连续三帧确认、人员冷却、SQLite 事务和唯一事件键完成签到/签退幂等。界面提供人员登记、人脸框、三秒手动签退、查询、UTF-8 CSV 和本机抓拍。当前已完成 30 分钟摄像头量化回归、真人业务回归和脱离开发 PATH 的便携包启动验证。系统定位上，它不抢占 RK3568 的摄像头或 NPU，未来只作为可配置 RTSP 的下游只读客户端；真实 RTSP 联调仍等待上游接口验收。”

## 13. 为什么视频会越运行越卡？你如何解决背压问题？

**问题**：人脸检测、特征提取和数据库判断比摄像头取帧慢时，如果每帧都排队，显示的会越来越旧，用户感觉就是“越跑越卡”。

**做法**：预览和识别分频。预览约 25 FPS；识别默认每 200 毫秒最多投递一次，同时只保留一个待处理任务，新的识别机会直接丢弃而不是排队。跨线程帧仍使用 `cv::Mat::clone()`，显示缩放改为快速模式。

**价值**：这是一种实时系统中的“保新不保全”策略：宁可跳过旧帧，也不能让实时预览延迟不断累积。

**边界**：当前已给出一次本机摄像头 30 分钟 CPU、内存、FPS 和识别延迟量化结论，但只代表当前机器与场景；此前摄像头黑流的确定根因和跨机器表现仍未验证。

## 14. 为什么 MP4 能播放但 OpenCV 打不开？

**问题**：用户提供的 H.264 MP4 可在播放器播放，但当前 Qt/OpenCV 4.5.2 组合打开失败。

**做法**：先区分“容器格式”与“编码器”。`.mp4` 只是容器，H.264 是视频编码；不同软件编译时是否带相应解码器不同。保留原视频不修改，并生成 Git 忽略的 MJPEG AVI 兼容副本用于开发，项目测试读完 461 帧。

**价值**：把第三方解码能力差异转为可复现的输入兼容性问题，而不是盲目怀疑 Qt 或人脸算法。

**边界**：不能据此宣称所有 H.264/MP4 都支持；真实 RTSP 的 H.264 解码必须在网关接口可用后单独验证。

## 15. 为什么 Qt Creator 编译成功后仍可能启动崩溃？

**问题**：编译/链接成功不等于运行环境完整。Qt Creator 的运行配置默认未必带上 OpenCV、SeetaFace DLL、模型目录、SQLite 插件和数据目录。

**做法**：开发阶段统一由 `run-dev.ps1` 设置环境并启动；Qt Creator 的本机私有 `.pro.user` 配置同步这些变量。发布阶段由打包脚本显式复制 DLL、平台插件、SQL 驱动和模型。

**价值**：把“能编译”和“能交付运行”作为两个可验证阶段管理。

**边界**：`.pro.user` 是机器私有文件，必须 Git 忽略；换电脑必须重新配置，不能提交或复制别人的绝对路径。

## 16. 为什么同时有自动签退和“确认 3 秒”的手动签退？

**问题**：自动状态机默认要求签到后间隔 4 小时才签退，适合避免误操作，却不利于短时间演示。

**做法**：保留自动规则，额外增加显式手动签退。按钮只在视频播放且已经识别到登记人员时可点；点击后固定候选工号，只有单人、同一身份连续识别满 3 秒才调用仓储层写库。人员变化、无人脸、未签到或视频停止都会取消/拒绝。

**价值**：展示层的快捷操作没有绕过业务层规则，最终仍由事务、唯一键和当天状态保护数据。

**边界**：三秒规则、负向中断和重复抑制已有内存 SQLite 自动测试，用户也已完成真实摄像头 UI 人工验收；自动化日志与用户现场反馈在实施记录中分开标注。

## 17. 旧界面为什么会显示不存在的人员？现代化改造如何不破坏业务？

**问题**：原示例 UI 写死了“007 / 何青德”等课程演示占位文本，且使用固定坐标和默认衬线字体，容易让人误以为系统已识别到人员，也造成裁切重叠。

**做法**：保留现有业务对象名、信号、槽和数据访问逻辑，只替换界面容器：左侧媒体卡片、右侧 `QTabWidget`（识别/注册/查询），用布局管理器处理自适应。`Theme` 集中提供浅色、白卡片、蓝主色和 Microsoft YaHei UI 的 QSS；识别成功才从 SQLite 加载注册头像和人员字段。

**价值**：界面职责和业务职责分开，后续换样式不会重写识别和考勤逻辑。

**边界**：已在 1280×720 做过检查；极端 DPI、小窗口和多语言仍要单独回归。

## 18. 摄像头设备显示正常但为什么仍会输出黑帧？

**问题**：Windows 设备管理器显示 `HP 5MP Camera` 正常，OpenCV 也报告已打开 `640x480 YUY2`，但采样像素均值是 `0,0,0`，这说明“打开设备句柄”不等于“拿到有效图像”。

**做法**：用 Windows 原生 `MediaCapture` 与 OpenCV DirectShow 两条独立采集链路取样；记录驱动重枚举、原生错误和黑帧证据，并在应用侧将连续近黑帧识别为输入异常，走有限重连而不是继续把黑帧送入识别。

**价值**：把设备枚举、采集协商和有效画面分层验证，避免把驱动会话问题误判成人脸算法或 UI 问题。

**边界**：本轮恢复后已完成一次 30 分钟回归，但不能从有限证据断言唯一根因，也不能保证其他机器或驱动版本不会复发。

## 19. 如何判断板端 MPP H.264 故障是在硬件、配置还是内存接口？

**问题**：网关能打开 V4L2 视频和 ALSA 音频，却在 MPP 配置或提交帧时失败。直接把问题归咎于“编码器坏了”会掩盖 SDK/ABI 参数差异。

**做法**：先运行板端官方 `mpi_enc_test` 编码一帧 NV12，得到 H.264 输出且退出码为 0，证明 RKVENC 硬件与板端 MPP 可用。再以官方样例为基准修正网关的帧率配置键、DRM 缓冲区类型、RGA 像素步长，并排查每帧输出包元数据。

**价值**：把“硬件能力”与“自研程序适配”分开，排障从猜参数变成有对照的 ABI 验证。

**边界**：网关的配置阶段已推进到运行态，但当前输出包补丁未完成并未重新构建；不能表述为网关已稳定产出 H.264 或已提供 RTSP。

## 20. 为什么不能把 H.264 文件输出直接称为 RTSP 服务？

**问题**：编码后的 `.h264` 只是压缩视频字节，客户端还需要通过 RTSP 协议发现会话、获取媒体描述并持续读取 RTP 数据。

**做法**：先验证网关持续输出可解析的原始 H.264，再选择独立、只读的 RTSP 发布组件或在网关中实现明确的服务端模块；最后才让 Qt 客户端填写 URL 做只读拉流。

**价值**：媒体编码和网络服务边界清晰，Qt 不需要抢占板端摄像头、NPU 或编码器。

**边界**：目前板端没有监听 554/8554，`rtsp://192.168.50.2:8554/live` 尚不存在；真实 RTSP 联调未验证。

## 21. 遇到非 Git 网关源码和中断补丁时如何保持可追溯？

**问题**：指定网关源码目录没有 `.git`，且中断发生在 MPP 输出包错误分支，若继续编译会首先遇到语法错误。

**做法**：不删除已有目录和证据，记录精确源码路径、未闭合位置、运行过的官方样例和下一步恢复顺序；Qt 仓库仅提交交接文档，不把它误称为网关源码提交。

**价值**：避免把“文档已推送”误报成“网关代码已版本化”，也让接手者能从可编译状态开始恢复。

**边界**：后续应先取得网关源码的正式版本控制方式或创建经负责人确认的独立仓库；在此之前，任何网关代码变更都只能作为现场证据记录。

## 22. 为什么要把视频读取和存储写入移出 UI 线程？

**问题**：初版只有界面线程和一个识别线程，视频源读取、考勤写库、抓拍保存全部在界面线程执行。本地文件和摄像头尚可接受，但真实 RTSP 网络抖动或磁盘变慢时会阻塞界面，也无法支撑"多线程流水线"的表述。

**做法**：拆成 4 线程模型——UI（界面与决策）、`VideoSourceWorker`（视频源打开/轮询/关闭）、`QFaceObject`（检测/跟踪/质量/识别）、`AttendanceWriter`（考勤写入与抓拍，使用**独立 SQLite 连接**，"独立"是因为 Qt SQL 连接有线程亲和性，不能跨线程共用）。跨线程只传值类型与 `cv::Mat`，结果经信号回传 UI；识别链路增加串行门控，避免下一轮跟踪任务排在当前查询之前造成乱序。

**价值**：界面线程不再执行任何阻塞 I/O；这也是面试中"你的多线程是怎么设计的"最有说服力的部分——不是简单丢一个 QThread，而是按 I/O 类型切分并处理连接亲和性。

**边界**：真实网络条件（抖动、丢包）下的界面流畅度与延迟仍需在联调环境实测。

## 23. 如何发现并修复"假通过"的自动化测试？

**问题**：质量门控测试用合成色块图做人脸样本，SeetaFace 检测器完全检测不到目标，测试断言全部进入跳过分支，用例仍然"通过"，等于没有验证。

**做法**：改用真实人脸夹具视频帧作为基线，先验证基线帧能被检测且策略放行，再对同帧做工程化退化（暗光、过亮、高斯模糊、缩小人脸矩形），断言每类退化必须被对应告警拦截；同时补充纯策略单元测试覆盖边界。

**价值**：测试的价值在于"能失败"。能用真实样本构造负例，比增加用例数量更重要；面试中这是"你怎么保证测试有效性"的直接答案。

**边界**：合成退化与真实低质量画面的判定差异仍存在，真实场景阈值需要用采集样本继续标定。

## 24. 算法预检查过严时怎么做工程取舍？

**问题**：SeetaFace 质量评估的姿态门限非常保守，人脸约 12 度歪头就被标记姿态告警；若识别流程把它当作硬门限，正常用户会被反复拒绝，体验和可用性都不可接受。

**做法**：抽出 `FaceQualityPolicy` 把"质量检查"与"业务策略"分开：识别流程只拦截亮度、尺寸、清晰度，姿态告警交由识别模型容忍；注册流程保持严格（四项全检 + 单人脸），确保特征库质量。阈值可配置。

**价值**：算法组件的判定不等于业务决策；工程上应该按场景选择门限，而不是全盘接受算法输出。这也是"算法与业务分层"的典型例子。

**边界**：姿态容忍度对识别准确率的实际影响需要用真实歪头样本评估。

## 25. 发现文档里的性能数据不可复现时怎么办？

**问题**：旧记录写"平均识别延迟约 21ms"，按同样步骤在新旧代码上都复现不出，实际约 400-480ms。

**做法**：设计对照实验——用 git worktree 检出旧提交构建旧版程序，与新版在相同夹具、相同环境下各跑一次；结果 30 帧、3 次请求，旧版平均 478ms、新版约 400ms。随后用临时埋点确认延迟主体来自 SeetaFace `QueryTop` 的 CPU 推理（单次 402-418ms），排除线程和队列因素。最后更正文档并规定只写可复现数据。

**价值**：性能数字必须能指出来源和测量方法；发现旧数据有误时主动更正并记录证据，比保留一个好看的数字更重要——面试官追问测量方法时不会翻车。

**边界**：该数据只代表当前机器与夹具；跨机性能差异需另行测量。

## 26. 工具链缺少解码后端时如何选择方案？

**问题**：本机 OpenCV 构建无 FFMPEG/GStreamer 后端，`cv::VideoCapture` 打不开任何 `rtsp://` 地址。可选方案有三种：重建 OpenCV、引入独立 ffmpeg 子进程、换 LibVLC。

**做法**：先写探测程序确认根因（`getBuildInformation` 显示 `FFMPEG: NO`），再比较成本：重建 OpenCV 需要获取 MinGW 版 FFmpeg 开发库并重新编译（小时级、影响既有环境）；LibVLC 引入大型第三方库；ffmpeg 子进程只需一个可执行文件，且与原状态机解耦。选定子进程方案：`ffmpeg -rtsp_transport tcp -i <url> -f rawvideo -pix_fmt bgr24 -`，从 stdout 按帧读取；连接以首帧到达为准，读取带无数据看门狗与缓冲上限。

**价值**：这是"受限环境下的技术选型"案例——列出候选、评估成本与风险、选择可验证的最小方案，而不是追求最"正统"的做法。

**边界**：子进程方案有额外进程开销和发布包体积成本；完成联调前不能表述为"OpenCV 已支持 RTSP"。

## 27. 为什么 FFmpeg 不能做 RTSP 服务端？

**问题**：本地回环验证时尝试用 `ffmpeg -rtsp_flags listen` 自建 RTSP 服务器，端口始终没有监听，客户端连接被拒。

**做法**：查证 FFmpeg 实现：`listen` 选项只存在于 demuxer（接收侧），muxer（发送侧）只能向服务器推流；因此正确拓扑是"推流端 → 独立流媒体服务器 → 拉流端"。本机用 MediaMTX 验证，跨项目用 ZLMediaKit（网关无需改代码，换推流目标即可）。

**价值**：这是媒体架构的常识性知识点，面试中能讲清"推流/拉流/服务端"的角色划分和 FFmpeg 的边界，比只会调 API 更有说服力。

**边界**：独立服务器带来额外部署组件；实际项目需评估运维成本。

## 28. 如何做跨机端到端联调并保护他人环境？

**问题**：需要在 VM（Ubuntu 网关）与 Windows 控制台之间做真实跨机验证，但同一台 VM 可能有其他并行会话（构建容器、既有媒体容器），直接操作会互相干扰。

**做法**：① 用唯一命名的测试容器与端口（`qt-e2e-zlm`，8654）与既有容器隔离；② 网关测试使用唯一目录、唯一配置和日志，先检查进程与端口，不停止既有实例、不覆盖部署目录；③ 修正示例配置与文档不一致的推流路径后，先验证单机推流稳定（120 秒、0 错误），再从 Windows 拉流（415 帧），最后用带人脸的流完成识别验证（30 次请求/29 次返回，平均约 492ms）。

**价值**：这是"在多任务环境中有纪律地验证"的案例；唯一命名、隔离端口、保留证据，面试中可以体现工程规范性。

**边界**：属于 PC 回环 + Mock/夹具源验证，不代表板端真实设备与网络条件。

## 29. 流媒体"两个方向"如何在简历中讲清楚？

**问题**：项目 1（网关）与项目 2（控制台）都涉及流媒体，如果讲不清分工，会被认为重复；如果只讲拉流，又缺少服务端方向的深度。

**做法**：按方向拆分：**服务端/推流方向（项目 1）**——网关用 FFmpeg RTSP muxer 推流到 ZLMediaKit，由其完成多协议分发（RTSP/HTTP-FLV/RTMP/HLS），PC 阶段已验证 3 路并发拉流、ZLM 重启后自动重连、服务端占用 CPU 5.6%/内存 8.5MB；**客户端/拉流方向（项目 2）**——控制台用独立 FFmpeg 子进程拉流解码，完成识别与考勤业务，本机回环 9/9 与跨机 30 次识别请求。两端合起来覆盖"推流—分发—拉流"完整链路。

**价值**：一个方向讲媒体服务与多协议分发，一个方向讲客户端解码与业务落地，职责不重叠、技术栈互补，正好回答"两个项目为什么不是重复的"。

**边界**：只写已复现的实测数字；板端尚未复核、真实网络条件未验证的部分明确标注"待验证"。
