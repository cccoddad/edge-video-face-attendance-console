# 项目问题汇总（通俗版）

本文记录的是本次整理和升级过程中真实碰到的问题。每一项都分清“已经解决”“暂时规避”和“等待外部条件”，避免把还没完成的计划当成成果。

## 1. 原项目不需要为了升级立刻换 Qt6

**现象**：电脑已经安装 Qt 5.12.0，但项目资料中出现过 Qt 5.14.2 的下载说明，容易误以为必须换 Qt6 才能继续。

**原因**：Qt5 小版本之间确实可能有兼容性差异，但现有工程使用的是 Qt Widgets、Qt SQL 等成熟 API，并没有 Qt6 才具备的刚性需求。

**处理**：先在本机 Qt 5.12.0 + MinGW 7.3 环境构建并通过启动验证。Qt6/CMake 是未来可独立规划的迁移项，不混入当前功能升级。

**状态**：已解决。

## 2. 第三方依赖路径不适合直接写进工程

**现象**：OpenCV 和 SeetaFace 位于课程资料目录，其中含中文路径；原工程还依赖固定的本机目录。

**原因**：老 Qt/qmake 和 MinGW 工具链对中文路径、不同盘符和个人目录迁移不友好；硬编码路径会让项目只能在一台电脑运行。

**处理**：建立本机 `D:\qtdeps` 入口，并将真实依赖位置写入被 Git 忽略的 `third_party.pri`。仓库提供 `third_party.pri.example` 作为新环境的填写模板。

**状态**：当前电脑已解决；新电脑仍需按实际依赖位置配置。

## 3. 模型目录原先写死，换机器会直接识别失败

**现象**：人脸模型曾依赖固定目录，程序找不到模型时不能给出清楚原因。

**原因**：模型文件被当作“永远在同一位置”的资源，而不是可配置的运行依赖。

**处理**：新增应用配置模块，支持 `FACE_ATTENDANCE_MODEL_DIR`；启动时逐个检查三个必要 `.dat` 模型并显示缺失文件和当前目录。

**状态**：已解决。

## 4. 考勤表字段名称前后不一致

**现象**：代码写入或读取考勤时间时，字段名存在不一致，可能造成 SQL 执行失败或查询不到刚写入的记录。

**原因**：原示例的数据表定义和业务代码没有作为一个整体维护。

**处理**：按现有数据库字段 `checktime` 统一考勤时间读写，并将数据库路径收敛到应用配置。

**状态**：已修复；后续变更表结构时需要配套迁移脚本。

## 5. SQL 字符串拼接有数据和安全风险

**现象**：人员编号、姓名等输入若直接拼入 SQL，包含引号时可能导致语句报错，也会留下注入风险。

**原因**：示例项目为了快速演示省略了正式应用应有的参数绑定。

**处理**：注册和考勤写入改用预编译 SQL、绑定参数和事务。

**状态**：核心写入已处理；新增查询或导出功能时必须延续同一规则。

## 6. 异步识别线程可能读到被覆盖的图像

**现象**：摄像头或视频采集持续产生帧，识别比采集慢时，线程间直接传递 `cv::Mat` 容易让后台任务读到已被下一帧复用的内存。

**原因**：`cv::Mat` 是引用计数对象，直接传递不等价于深拷贝；示例项目没有明确采集线程和识别线程的所有权边界。

**处理**：向识别任务投递克隆后的帧，并在退出时等待线程结束。

**状态**：已修复基础生命周期问题；后续接入文件或 RTSP 输入时还要通过有界队列控制延迟和内存。

## 7. “最像的人”不一定是真正识别成功

**现象**：即便画面里是陌生人，算法也总能在已登记人员中给出最高分；如果没有阈值，系统会误签到。

**原因**：相似度排序和身份确认是两件事，示例项目缺少业务阈值。

**处理**：增加可配置相似度阈值，默认 `0.70`；低于阈值显示为未知人员。

**状态**：已完成第一层保护；阈值必须依据真实采集样本测试后调整。

## 8. 连续画面会重复产生考勤

**现象**：一个人站在镜头前数秒，系统会识别到很多帧，若每帧都写数据库就会出现大量重复记录。

**原因**：原示例只做了单帧识别，没有完整的业务去抖和幂等规则。

**处理**：已加入三层保护：同一人需要连续 `N` 帧确认（默认 3 帧）、内存中的人员冷却时间（默认 30 秒），以及 SQLite 中按人员/日期/事件组成的 `event_key` 唯一索引。当天第一条有效事件写签到；自动签退受最小间隔限制，演示用的手动签退还必须持续确认 3 秒。

**状态**：已完成代码与内存 SQLite 自动化测试；真实摄像头下的长时间人工回归仍待补充。

## 9. 没有摄像头不是 Qt 程序当前的故障

**现象**：Windows 程序显示没有摄像头画面。

**原因**：物理 UVC 摄像头一直插在 RK3568 板上，由网关项目独占；Windows 本来就不应直接访问该设备。

**处理**：将最终架构明确为 Qt 通过 RTSP 只读拉流。本地开发阶段已实现本地视频文件和 Windows 本机摄像头两种输入；本机摄像头只用于独立开发，不连接、不枚举也不抢占 RK3568 上的设备。

**状态**：`IVideoSource`、`VideoFileSource`、`LocalCameraSource` 已实现并完成冒烟验证；`RtspSource` 仅完成 URL 校验和状态机预留，未连接真实流。

## 10. 网关当前还没有正式 RTSP 视频流

**现象**：电脑和 RK3568 已通过千兆网线互通，但 Qt 不能立即拉取目标 RTSP 地址。

**原因**：网关项目目前已验证摄像头、麦克风、MJPEG 解码、RKNN 与校验输出；真正的 H.264 编码和 RTSP 服务端仍属于网关项目后续实施与验收内容。

**处理**：Qt 项目不碰板端，先完成本地视频、RTSP 客户端代码、断流重连和业务状态机。网关正式提供并验收 `rtsp://<rk3568-ip>:8554/live` 后再做只读联调。

**状态**：等待网关项目。

## 11. SSH 端口可达但不能作为板端操作通道

**现象**：电脑到板子 `192.168.50.2` 的网络与 TCP 22 端口可达，但 SSH 在服务端横幅交换阶段超时。

**原因**：这通常是板端 Dropbear/SSH 服务状态、网络转发或旧系统兼容性问题；不能仅凭端口可达就判断远程 Shell 可用。

**处理**：Qt 项目不依赖 SSH，也不会借此操作板子。需要板端检查时，应由网关项目使用已验证的 SecureCRT 串口链路处理。

**状态**：已规避，不影响 Qt 本地开发。

## 12. Windows 发布不能只复制 exe

**现象**：Qt 程序在开发机能运行，复制一个 `FaceAttendance.exe` 到其他目录可能因缺 Qt 平台插件、SQLite 驱动、OpenCV/SeetaFace DLL 或模型而启动失败。

**原因**：Qt/MinGW 应用在 Windows 上依赖一组动态库、插件和模型资源。

**处理**：增加 Windows 打包脚本，显式复制运行所需 DLL、`platforms/qwindows.dll`、`sqldrivers/qsqlite.dll` 和人脸模型，并完成独立启动验证。

**状态**：当前依赖版本已验证；更换 Qt、OpenCV 或 SeetaFace 版本后必须重新验证打包清单。

## 13. 两个项目同时运行的资源冲突风险

**现象**：网关运行采集和 RKNN 推理时，若 Qt 项目也试图在板端采集、推理或开启 RTSP 服务，会出现设备被占、NPU 过载、端口冲突或测试证据混乱。

**原因**：两个项目最初都与视频和视觉有关，但职责未明确时很容易重复占用资源。

**处理**：建立强制协作边界：网关优先，Qt 仅 Windows PC 端读取；两者不共享设备、NPU、端口、目录、SQLite、模型和日志。

**状态**：规则已写入仓库；后续跨项目动作必须先获得用户确认。

## 14. 启动时出现了“007 / 何青德”等陌生人物信息

**现象**：还没有打开视频或完成识别，右侧却已经显示一个具体人员编号、姓名和部门，看起来像系统凭空识别了人。

**原因**：原课程示例把演示用人物文字直接写在界面文件中，作为排版占位内容；这不是数据库读到的人，也不是识别模型的结果。

**处理**：移除静态人物占位信息。启动、无脸、未知人脸和识别中分别显示对应的中性状态；真正识别成功后才从 SQLite 人员记录读取头像、姓名、工号和部门。

**状态**：已修复。若再次出现具体人员信息，应检查是否已经触发真实识别或是否仍在显示上一帧结果，而不是认为模型“自动认识”了陌生人。

## 15. 有 MP4 文件却提示 OpenCV 无法打开

**现象**：`authorized-face.mp4` 在电脑上可以播放，但 Qt 程序通过当前 OpenCV 4.5.2 打不开。

**原因**：能否播放不只取决于文件扩展名。该 MP4 使用 H.264 编码，Windows 播放器/Python 环境和 Qt 当前绑定的 OpenCV 构建所带解码能力不同；后者没有可用的 H.264 解码链路。

**处理**：不修改原 MP4，另外生成 Git 忽略的 MJPEG AVI 兼容副本供本机开发使用。项目测试已验证这个 AVI 可连续读完 461 帧。程序仍会对打不开的视频显示完整文件路径和失败原因。

**状态**：当前环境已规避。不是“所有 MP4 都不能用”，而是必须在项目自己的 OpenCV 环境中实际打开验证。

## 16. 注册页点“拍照”很久没有反应，窗口像卡住

**现象**：视频播放中点击拍照或注册后，按钮没有及时变化，Windows 还可能标记窗口“未响应”。

**原因**：旧交互没有先检查视频是否仍有有效帧，且人脸跟踪、特征提取等较耗时工作在界面线程同步等待时，会阻塞窗口绘制和鼠标响应。

**处理**：拍照前检查视频播放状态和当前帧；没有有效帧时立即说明原因。人脸跟踪和注册改为通过 Qt 信号槽异步执行，按钮会显示“正在注册...”或“已拍照，可注册”。修改工号、姓名、部门后自动使旧照片失效，避免照片和人员资料错绑。

**状态**：已修复主要卡顿与提示缺失问题；低性能电脑上的实际识别耗时仍受模型和 CPU 性能影响。

## 17. 视频运行越久越卡

**现象**：摄像头刚打开时画面流畅，运行一段时间后预览明显落后于现实。

**原因**：如果每一帧都投给人脸检测、特征提取和数据库判断，后台处理速度小于采集速度时，待处理任务会积压；高质量缩放也会额外占用 UI 线程。画面不是网络“变慢”，而是旧帧排队造成显示延迟。

**处理**：预览保持约 25 FPS，但识别投递默认限制为每 200 毫秒最多一次；同一时刻只允许一个待处理识别请求，后续帧直接丢弃识别机会而不排队；显示缩放使用快速模式。`FACE_ATTENDANCE_RECOGNITION_INTERVAL_MS` 可在 100 至 1000 毫秒间调节。

**状态**：代码和人工演示均已完成，并在本机摄像头 `#0` 上连续运行 `1800.342` 秒：读取 `38380` 帧，平均 `21.318 FPS`；识别请求/返回 `379/379`，平均延迟 `13.549 ms`、最大 `32 ms`；CPU 平均 `1.252%`、最大 `1.696%`，工作集 `188.250-202.930 MB`。本轮没有逐渐卡顿或视频源错误，但这些数据只代表当前电脑、摄像头驱动和测试场景，不能承诺所有机器固定帧率。

## 18. Qt Creator 中编译成功，但点击运行后程序崩溃

**现象**：Release 程序可构建，Qt Creator 的“应用程序输出”却显示进程已结束或 crashed。

**原因**：编译通过只说明代码和链接库正确；运行时仍需要能找到 Qt/OpenCV/SeetaFace DLL、SQLite 插件、模型目录和本地数据目录。开发脚本会设置这些运行环境，Qt Creator 默认运行配置未必继承。

**处理**：使用项目 `scripts/run-dev.ps1` 验证开发启动；在 Qt Creator 的本机私有 `.pro.user` 运行环境中补齐同一组路径/变量。该文件是每台电脑的个人设置，已被 Git 忽略，不能提交到仓库。Windows 打包则由 `scripts/package-windows.ps1` 显式复制依赖。

**状态**：当前电脑已解决。若换电脑，应按 `third_party.pri.example` 和启动脚本重新配置，而不是复制他人的 `.pro.user` 文件。

## 19. 旧界面文字裁切、控件重叠且像课程作业

**现象**：原窗口使用默认衬线字体、绿色背景和大量固定坐标。在不同窗口尺寸下，标题、注册页和查询页容易互相遮挡。

**原因**：`setGeometry` 固定坐标适合一次性示例，不会随着字体、DPI、窗口大小或页面内容变化自动调整。

**处理**：使用 `QHBoxLayout`、`QVBoxLayout`、`QGridLayout` 和 `QTabWidget` 重建页面层级；把颜色、字体和控件状态集中到 `Theme` 的 QSS 中，统一为浅色背景、白卡片、蓝色主操作色和 Microsoft YaHei UI。窗口按 1280×720 设计，并设置最小尺寸。

**状态**：已完成构建和交互式视觉检查。极端缩放比例、多语言文本和更小窗口仍属于后续 UI 回归范围。

## 20. 原有自动签退规则不适合现场演示

**现象**：自动考勤为了避免刚签到就签退，默认要求签到后间隔 4 小时；演示时无法立即展示签退结果。

**原因**：自动状态机强调日常业务合理性，而课堂或答辩演示需要一个可见、且不会一点击就写库的签退路径。

**处理**：保留原自动规则，另外增加“签退（确认 3 秒）”。点击后固定当前已识别人员，必须单人、持续识别为同一人满 3 秒才写入；换人、无人脸、停止视频或未签到会立即取消或拒绝。数据库仍使用事务和唯一键，不能靠按钮状态绕过业务规则。

**状态**：状态机自动测试已覆盖三秒边界、人员变化、未签到拒绝和已签到签退；完整现场人工签退演示仍建议在下一轮按检查表补录。

## 21. Qt 5.12 工具链被删除后项目不能构建

**现象**：`qmake.exe` 和 `mingw32-make.exe` 在原 `D:\QT` 路径不存在，`scripts/build-qt5.ps1` 明确报 Qt 5.12 + MinGW 7.3 工具链未找到。

**原因**：这个工程的 `.pro` 文件、第三方 DLL 和既有验证都绑定 Qt 5.12/MinGW 7.3；只安装 Qt6 不能直接替代旧构建环境。

**处理**：恢复安装 Qt 5.12.0 的 MinGW 7.3 64-bit 组件，并使用原脚本构建。没有把工程迁移到 Qt6。

**状态**：已恢复并完成既有 Release 构建与测试；换电脑仍必须先安装匹配工具链。

## 22. Windows 摄像头能打开但画面是全黑

**现象**：`HP 5MP Camera` 在设备管理器显示正常，OpenCV DirectShow 也能协商到 `640x480 YUY2`，但探针 BGR 均值为 `0,0,0`，程序会显示“正在播放视频”而预览为黑色。

**原因**：证据不能支持单一根因。期间出现过驱动会话异常、设备短暂消失和原生采集错误；外接摄像头冲突、权限、物理挡片和 DirectShow Bridge 开关都没有被证实为唯一原因。

**处理**：用 Windows 原生 `MediaCapture` 与 OpenCV 两条路径分别采样，重启 USB 复合设备并重新枚举；应用侧增加近黑流检测和有限重连。恢复后完成 30 分钟量化回归。

**状态**：当前电脑恢复可用，但“为什么会复发”未验证，不能承诺永不再出现黑流。

## 23. 想连 RTSP 时板端其实没有 RTSP 服务

**现象**：开发板 IP 为 `192.168.50.2`，但 `ss` 没有 `554/8554` 监听，启动 `rk356x-demo` 后也没有新增 RTSP 端口。

**原因**：现有网关配置只把 H.264 写成原始文件证据，没有实现 RTSP 协议服务。`rk356x-demo` 是板卡演示程序，不会自动提供 `rtsp://192.168.50.2:8554/live`。

**处理**：Qt 端只保留可配置、显式触发的 RTSP 客户端状态逻辑；网关端先排查 H.264 编码，再单独实现只读 RTSP 输出。

**状态**：真实 RTSP 地址、网络拉流、断流重连和端到端人脸考勤均未验证。

## 24. 网关 MPP 配置拒绝 H.264 编码

**现象**：网关已打开 V4L2 和 ALSA，但在配置编码器时失败：`MPP rejected H.264 encoder configuration`，原始 H.264 文件没有产生。

**原因**：网关编译时使用的 MPP 头文件/参数习惯与板端实际 MPP 库不完全匹配。例如板端接受 `rc:fps_in_denorm`，而旧代码使用了不兼容的键；本地定义的 DMA 缓冲区标志也不能直接推断为板端可用值。

**处理**：以板端官方 `mpi_enc_test` 的真实运行结果为准，修正帧率参数和编码设置，确认官方样例能编码一帧 NV12 为 H.264。网关程序已能跨过最早的配置阶段进入运行态。

**状态**：硬件编码能力已验证；网关完整编码输出未验证，不能说“MPP 已修复完成”。

## 25. RGA 转色与 MPP 内存接口不匹配

**现象**：MPP 配置通过后，RGA 曾报 `Bad address`，后续又出现 `encode_put_frame` 拒绝输入帧或阻塞等待输出。

**原因**：RGA 的 RGB 步长单位是像素，不是字节；MPP 输入需要与板端匹配的 DRM DMA 缓冲区和输出包元数据。动态加载版本还无法取得官方静态样例内部使用的同步符号。

**处理**：把 RGB 步长改为 `frame.stride / 3`，按官方样例使用 `MPP_BUFFER_TYPE_DRM`，并开始给每帧绑定 MPP 输出包。

**状态**：RGA 的 `Bad address` 已消失，后续输出包补丁尚未重新构建；当前网关源码有未闭合错误分支，下一位开发者必须先修复编译状态。

## 26. 网关源码没有 Git 记录且最后一次补丁未完成

**现象**：指定网关目录不是 Git 仓库；最后一次编辑在 `mpp_rga_video_encoder.cpp` 的 `prepare_output_packet` 失败分支缺少完整错误返回，源码不能编译。

**原因**：网关工程以复制目录方式保存，缺少版本控制；长时间远程排障中补丁被中断。

**处理**：在 `09-RTSP与RK3568网关MPP排障交接.md` 记录精确路径、已验证命令结论、当前代码位置和恢复顺序。没有删除旧版本、旧日志或既有板端进程。

**状态**：Qt 文档可提交 Git；网关源码本身没有可提交仓库，不能宣称已推送其代码。
