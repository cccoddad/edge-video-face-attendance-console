## 1. 项目定位与双项目关系

控制台项目定位为**下游业务层**：把边缘视频源送来的画面，变成可追溯、可去重、可查询的考勤记录。

| 项目 | 最终定位 | 主要证据 | 对应简历主线 |
|---|---|---|---|
| RK3568 实时音视频边缘网关 | 边缘媒体接入层 | V4L2/ALSA、PTS 时间戳、RKNN/RGA、MPP/FFmpeg、MP4/RTSP、systemd 拉起 | 网关/边缘方向 |
| 多源视频人脸识别考勤控制台 | 上游业务决策层 | RTSP 客户端、Qt/C++ 多线程、识别流水线、SQLite 事件幂等、CSV 报表 | 上位机/业务方向 |

两个项目分别独立仓库、独立 README、独立验证证据和演示重点；控制台通过 RTSP 只读接口和未来的只读状态接口与网关协作。

**修订点（相对初版）**：初版把"6 张业务表 + 6 个线程 + 8 个模块目录"写成了既成事实。实际控制台侧当前为 **3 张 SQLite 表 + 2 个线程 + 单层 src/ 目录**（详见第 5、8、9 节）。本版将三者分别标注为已完成、待实现和下一阶段目标，避免简历表述与代码事实不符。

---

## 2. 为什么拆分两个项目

RK3568 网关侧已经承担视频采集、音频采集、时间戳治理、RKNN/RGA、MPP/FFmpeg、MP4、RTSP 相关和 systemd 恢复。若控制台仓库重复实现同一批能力，两个项目的设备层、媒体层、AI 层和运维层会同时膨胀，且面试中无法区分贡献。

| 重叠点 | 网关项目已承担 | 控制台侧明确边界 |
|---|---|---|
| 设备层 | V4L2、UVC 摄像头、ALSA、USB 设备枚举 | 只通过 RTSP 和本地摄像头/文件做独立开发 |
| 媒体层 | H.264/AAC、MPP、FFmpeg、MP4 与 RTSP 服务 | 只读取和解码显示 RTSP 视频流，不做媒体服务端 |
| AI 层 | 板端 RKNN 目标推理 | 只做人脸检测、特征匹配的决策逻辑和结果输出 |
| 可靠性层 | systemd、设备恢复、看门狗、进程拉起 | 实现客户端视频源状态机、断流重连和故障事件记录 |

**结论**：控制台的关键能力应集中在"视频源抽象、识别流水线、数据一致性、业务语义"。

## 3. 系统边界与接口

- 控制台运行于 Windows PC，是下游只读客户端；不操作网关硬件、服务、端口、NPU、摄像头或板端文件。
- 控制台不写入网关数据库，不与网关共享源码；只通过 RTSP 地址和（未来的）只读 HTTP 状态接口协作。
- 当前最小可行接口只有一个 RTSP 地址（如 `rtsp://<网关IP>:8554/live`）；状态接口属于第二阶段可选项。
- 跨项目动作受 `05-RK3568协作边界.md` 强制约束；在网关验收接口前，真实 RTSP 联调保持"等待网关"状态。

### 5.3 重组原则与风险

- 只移动文件并更新 `.pro` 的 `SOURCES/HEADERS` 与 `include` 相对路径，不改代码逻辑。

- 重组为独立提交，完成后必须全量重建 12 项测试并跑通，再继续其他改动。

## 6. 视频源、RTSP、断流与状态覆盖

### 6.1 已实现（部分完成）

- `IVideoSource` 统一接口：`open/read/close/state/lastError/displayName`，界面不直接依赖 OpenCV `VideoCapture`。
- 三种实现：`VideoFileSource`（循环开关、播放结束状态）、`LocalCameraSource`（设备号、掉线重连、黑帧检测）、`RtspSource`（URL 校验、断流进入 `Interrupted`、按间隔进入 `Reconnecting`）。
- 状态枚举：`Closed/Opening/Playing/Ended/Interrupted/Reconnecting/Error/Stopped`，轮询策略函数 `shouldKeepPolling()` 已单测。
- `RtspConfigurationDialog`：地址格式校验与重连间隔配置，不发起连接。

### 6.2 下一优先项：RTSP 本地回环验证（待实现，不依赖网关）

使用本机 FFmpeg 将测试视频推成 RTSP 流（或本地 RTSP 服务器），验证：首次连接、连续读帧、主动断开后进入 `Interrupted`、按配置间隔重连成功、恢复读帧并恢复识别。通过该项后，"RTSP 客户端"从"代码就绪"升级为"本地已验证"，简历表述随之改写。

### 6.3 网关联调（等待网关）

- 网关输出 H.264 RTSP 并通过验收后，再执行真实断网恢复、跨网延时和解码兼容性验证。
- 在此之前不得在任何材料中把网关联调写为已完成。

## 7. 人脸注册、识别流水线与考勤状态机

### 7.1 识别流水线（已完成）

```
视频帧 → 单人脸跟踪（CSRT）→ 质量门控（SeetaQualityAssessor）
       → 特征匹配（FaceRecognizer）→ 连续 N 帧确认（AttendanceStateMachine）
       → 按人冷却 → SQLite 幂等写入 → 抓拍留证
```

| 规则 | 实现 | 测试 |
|---|---|---|
| 连续帧确认 | 默认 3 帧，可配置 1-10 | `AttendanceStateMachineTest` |
| 质量门控（识别） | 拦截亮度/尺寸/清晰度，容忍姿态告警 | `FaceQualityAssessorTest` |
| 质量门控（注册） | 四项全查 + 单人脸，拒绝多人和低质量照片 | `FaceQualityAssessorTest` |
| 按人员冷却 | 默认 30 秒，防重复识别 | `AttendanceRepositoryTest` |
| 手动签退确认 | 当前人员连续 3 秒正脸确认 | 手动流程（无自动化） |
| 未知人员 | 低于阈值显示"陌生人"，不写库 | 手动流程（无自动化） |

### 7.2 考勤状态机（已完成）

- 首次确认为签到；同一天再次确认且超过最小间隔（默认 4 小时）自动转为签退；已完成签退后重复确认抑制。
- 事件键 `number:日期:类型` 全局唯一，数据库唯一索引兜底。

### 7.3 注册流程（部分完成）

- 已完成：拍照 → 检测单人脸 → 脸图质量评估 → 注册特征 → 写入人员表（事务保护，失败回滚删除特征）。
- 待实现（非当前优先级）：人员暂停/停用标记、一人多模板、注册照片存本地照片库并统一路径管理。

## 8. 数据模型、迁移与隐私边界

### 8.1 实际 Schema（修订重点）

| 表 | 位置 | 字段 | 说明 |
|---|---|---|---|
| `user` | `attendance.db` | `number`(PK)、`name`、`partment`、`faceid`、`facepictrue`、`entertime` | 人员档案；字段名沿用初版历史拼写 |
| `recorduser` | `attendance.db` | `id`(PK)、`number`、`checktime` + `event_type`、`event_key`、`similarity`、`source_type`、`snapshot_path` | 考勤事件；后 5 列由迁移补齐，`event_key` 有部分唯一索引 |
| `schema_version` | `attendance.db` | `version` | `DatabaseMigration` 版本跟踪 |
| 人脸特征库 | `faces.db` | 由 SeetaFace2 自管理（不透明二进制） | 控制台通过 `Register/Query/Delete` 调用，不直接读写 |

**修订说明**：初版设想的 `person/face_template/attendance_event/attendance_daily_state/video_source/system_event` 七表设计不引入。理由：
1. `user/recorduser` 结构简单、已有测试覆盖，重命名会破坏已有演示数据；
2. 人脸模板交给 SeetaFace 自管理更稳，SQLite 不存二进制特征；
3. 每日签到签退状态用查询即可实时计算，不需要聚合表；
4. 系统事件由持久化运行日志（`runtime.log`）承担，视频源配置已由 `RtspConfigurationDialog` 管理。

### 8.2 迁移框架（已完成）

- `DatabaseMigration::migrate()`：创建 `schema_version` 表 → 读取当前版本 → 按序执行未完成迁移 → 更新版本号；幂等可重复调用。
- `AttendanceRepository::ensureSchema()` 委托迁移系统，移除原 ad-hoc `PRAGMA` 检查。

### 8.3 事务与幂等（已完成）

- 所有写入使用参数化 SQL 和事务；事件键唯一索引保证重复写入被抑制；
- `updateSnapshotPath` 校验影响行数为 1，失败回滚。

### 8.4 隐私与安全边界（保留初版）

- 仓库只使用虚构员工编号、虚构人脸和占位数据。
- 抓拍、数据库、日志、照片全部位于本地数据目录，不入版本控制。
- README 明确数据表用途与清理方式；演示视频遮蔽真实工牌和人员。
- 项目定位为考勤记录工具，不宣称"高安全门禁"。

## 9. 线程模型与可观测性（修订重点）

### 9.1 当前实际（2 线程）

| 执行单元 | 现状 | 位置 |
|---|---|---|
| UI 线程 | 界面、事件处理、**视频帧读取（40ms 定时器 + OpenCV 阻塞读）**、考勤决策、SQLite 读写、指标写盘 | `facerecognitionwin.cpp` |
| 识别线程 | 检测、跟踪、关键点、特征提取、质量评估 | `QFaceObject` 移入 `QThread` |

**已知风险**：`OpenCV VideoCapture::read()` 在 UI 线程执行。本地文件/摄像头尚可接受；真实 RTSP 网络抖动或缓冲区等待时会卡界面。这是当前架构与"多线程流水线"表述之间最大的差距。

### 9.2 目标（下一阶段执行）

| 执行单元 | 目标职责 | 关键约束 |
|---|---|---|
| UI 线程 | 界面渲染、用户交互、结果显示 | 不执行任何阻塞 I/O |
| 视频源线程（新增） | 打开/读取/关闭视频源，定时轮询，投递帧和状态信号 | 源对象在线程内创建销毁；跨线程只传 `cv::Mat` 和值类型 |
| 识别线程（已有） | 检测、跟踪、质量、特征 | 保持请求 ID 会话隔离 |
| 存储线程（新增） | 考勤写入、抓拍保存、路径回填、人员导入导出 | 使用独立 `QSqlDatabase` 连接（Qt SQL 线程亲和性要求）；写失败可被 UI 感知 |

### 9.3 实施步骤

1. **视频源线程**：新增 `VideoSourceWorker`（QObject + 内部定时器），把 `IVideoSource` 的创建、`open/read/close` 全部搬入工作线程；通过 `frameReady(cv::Mat)`、`sourceOpened`、`sourceOpenFailed`、`stateChanged`、`readFinished` 信号与 UI 通信；UI 侧改为缓存 `mVideoSourceState/DisplayName/Error`，不再直接调用源对象。
2. **存储线程**：新增 `AttendanceWriter`（QObject），持独立 SQLite 连接，槽函数执行 `record/recordCheckOut/updateSnapshotPath`；结果经信号回 UI。抓拍编码也移入该线程。
3. **回归验证**：12 项测试全部通过；夹具视频端到端运行帧数、识别请求/返回、延迟、退出码与重构前基线一致；重点确认无界面卡顿。

### 9.4 指标与可观测性（部分完成）

| 指标 | 现状 |
|---|---|
| 帧读取数、识别请求/返回数 | 已采集（性能日志 CSV） |
| 平均/最大识别延迟 | 已采集 |
| 考勤写入成功/抑制/失败计数 | 已采集 |
| 视频源状态与错误 | 已采集（性能日志 + 运行日志） |
| P95 延迟、预览 FPS、识别 FPS | 待实现（现有 CSV 可平滑扩展） |
| 数据库写入失败率 | 待实现（存储线程落地后补齐） |

性能日志通过 `FACE_ATTENDANCE_PERFORMANCE_LOG_PATH` 启用，按 `FACE_ATTENDANCE_PERFORMANCE_LOG_INTERVAL_MS` 间隔采样。

### 12.2 面试追问准备（边界清晰）

- **为什么不用控制台自己做 RTSP 服务端？** 媒体服务端归网关，控制台只做业务层，分开讲清贡献。
- **为什么不用单帧匹配直接考勤？** 单帧模型波动大；连续帧确认影响误识率、属可调参数。
- **如何避免重复考勤？** 业务冷却 + 数据库唯一事件键双保险。
- **RTSP 断流后发生了什么？** 状态机进入断流等待并暂停识别；重连成功恢复读帧后才恢复识别；运行日志有时间线。
- **为什么用 SQLite？** 单机、写入简单、够用；适合本项目的演示与离线场景。
- **隐私边界？** 当前没有可控门禁；仓库只用虚构数据；项目定位为考勤记录工具。
