## 1. 项目定位与双项目关系

控制台项目定位为**下游业务层**：把边缘视频源送来的画面，变成可追溯、可去重、可查询的考勤记录。

| 项目 | 最终定位 | 主要证据（2026-09-12 核实） | 对应简历主线 |
|---|---|---|---|
| RK3568 实时音视频边缘网关 | 边缘媒体接入层 + **流媒体服务层** | V4L2/ALSA 真实板端、RKNN、FFmpeg H.264/AAC、MP4、RTSP push（断连恢复/传输选项/超时守卫）、**ZLMediaKit 多协议分发（PC 阶段 1 验证）**、systemd、73 项测试、长稳 | **嵌入式音视频（推流/服务端方向）** |
| 多源视频人脸识别考勤控制台 | 上游业务决策层 + **流媒体客户端** | RTSP 客户端状态机（解码后端方案已定）、Qt/C++ 4 线程、识别流水线、质量门控、SQLite 事件幂等与迁移、CSV 报表、14 项测试 | **上位机 + 拉流/客户端方向** |

两个项目分别独立仓库、独立 README、独立验证证据和演示重点；控制台通过 RTSP 只读接口和未来的只读状态接口与网关协作。

**流媒体两个方向的互补（简历主线）**：

- **服务端/推流方向（项目 1）**：网关 `FFmpeg RTSP push` 推流到 **ZLMediaKit**，由其向多客户端分发 RTSP/RTMP/HTTP-FLV/HLS/WebRTC；PC 阶段 1 已验证 3 路并发与多协议播放。
- **客户端/拉流方向（项目 2）**：控制台从 RTSP 服务器拉流解码后做人脸识别与考勤；解码后端方案为独立 ffmpeg 子进程（已部署，实现与验证进行中）。
- 两个方向合起来覆盖"推流 → 分发 → 拉流"完整链路，且分属不同项目、不同技术栈，面试中可清晰区分贡献。

**修订点（相对初版）**：初版把"6 张业务表 + 6 个线程 + 8 个模块目录"写成了既成事实。实际控制台侧当前为 **3 张 SQLite 表 + 4 个线程 + 单层 src/ 目录**（详见第 5、8、9 节）。本版逐项标注已完成、进行中、待实现和等待板端状态，避免简历表述与事实不符。

## 2. 为什么拆分两个项目

RK3568 网关侧已经承担视频采集、音频采集、时间戳治理、RKNN/RGA、MPP/FFmpeg、MP4、RTSP 相关和 systemd 恢复。若控制台仓库重复实现同一批能力，两个项目的设备层、媒体层、AI 层和运维层会同时膨胀，且面试中无法区分贡献。

| 重叠点 | 网关项目已承担 | 控制台侧明确边界 |
|---|---|---|
| 设备层 | V4L2、UVC 摄像头、ALSA、USB 设备枚举 | 只通过 RTSP 和本地摄像头/文件做独立开发 |
| 媒体层 | H.264/AAC、MPP、FFmpeg、MP4、RTSP 推流与 ZLMediaKit 多协议分发 | 只拉流、解码与显示，不做媒体服务端 |
| AI 层 | 板端 RKNN 目标推理 | 只做人脸检测、特征匹配的决策逻辑和结果输出 |
| 可靠性层 | systemd、设备恢复、看门狗、进程拉起 | 实现客户端视频源状态机、断流重连和故障事件记录 |

**结论**：控制台的关键能力应集中在"视频源抽象、拉流解码、识别流水线、数据一致性、业务语义"。流媒体服务端与分发归网关侧（ZLMediaKit），客户端拉流归控制台，两个方向内容不重复。

## 3. 系统边界与接口

- 控制台运行于 Windows PC，是下游只读客户端；不操作网关硬件、服务、端口、NPU、摄像头或板端文件。
- 控制台不写入网关数据库，不与网关共享源码；只通过 RTSP 地址和（未来的）只读 HTTP 状态接口协作。
- 当前最小可行接口只有一个 RTSP 地址（如 `rtsp://<网关IP>:8554/live/camera`，ZLMediaKit 路径格式 `app/stream`）；状态接口属于第二阶段可选项。
- 流媒体职责划分：推流与服务端（ZLMediaKit）归项目 1；拉流与业务处理归项目 2。
- 跨项目动作受 `05-RK3568协作边界.md` 强制约束；网关侧 RTSP 推流 + ZLMediaKit 已在 **PC 阶段 1** 验证（本机 `D:\share\` 有证据），板端部署为阶段 2（待板端 MPP/RGA 与 RTSP 验证后）；与板端的真实联调仍标记为"等待板端"。

## 6. 视频源、RTSP、断流与状态覆盖

### 6.1 已实现（部分完成）

- `IVideoSource` 统一接口：`open/read/close/state/lastError/displayName`，界面不直接依赖 OpenCV `VideoCapture`。
- 三种实现：`VideoFileSource`（循环开关、播放结束状态）、`LocalCameraSource`（设备号、掉线重连、黑帧检测）、`RtspSource`（URL 校验、断流进入 `Interrupted`、按间隔进入 `Reconnecting`）。
- 状态枚举：`Closed/Opening/Playing/Ended/Interrupted/Reconnecting/Error/Stopped`，轮询策略函数 `shouldKeepPolling()` 已单测。
- `RtspConfigurationDialog`：地址格式校验与重连间隔配置，不发起连接。

### 6.2 RTSP 客户端解码后端（方案已定，实现进行中）

2026-09-12 探测确认：当前 OpenCV 4.5.2 MinGW 构建 `FFMPEG: NO`、`GStreamer: NO`、仅 `DirectShow: YES`；`cv::VideoCapture::open("rtsp://...")` 直接返回失败。原因不是网关，而是本机 OpenCV 缺少网络流解码后端。

**根因澄清**：FFmpeg 的 `-rtsp_flags listen` 仅存在于 demuxer（输入侧），muxer 只能向服务器**推流**、不能监听（网关侧同样结论，参见网关 docs 65 与 `09` 交接）。因此"本机自己当 RTSP 服务器"不可行，正确拓扑是：**推流端（网关/ffmpeg）→ 独立流媒体服务器（ZLMediaKit / 轻量备选 MediaMTX）→ 拉流端（控制台）**。

**已选方案（方案 B，用户已批准）**：引入独立 `ffmpeg.exe`，`RtspSource` 改为子进程管道解码（原始 BGR 帧流）。

- 已完成：ffmpeg 部署到 `D:\qtdeps\ffmpeg\bin\`（BtbN master `N-126497-g5b614efc7e-20260911`），验证 h264 解码、libx264 编码、rtsp 输入/输出均可用；
- 待实现：`RtspSource` 的子进程改造（保留现有状态机与断流重连逻辑）；
- 待验证：本地回环（ffmpeg 推流 → ZLMediaKit/MediaMTX → 控制台拉流）与跨项目联调（网关 → ZLMediaKit → 控制台）。
- 完成验证前，`RtspSource` 只能表述为"客户端状态机代码就绪、解码后端实现进行中"，不得表述为"已验证"。

### 6.3 网关联调（PC 链路已验证，板端待复核）

- 已验证（PC 阶段 1，证据在 `D:\share\`）：网关零代码改动推流至 ZLMediaKit，3 路客户端并发 RTSP 拉流、HTTP-FLV/RTMP/HLS 播放、ZLM 重启后网关 `connection_lost=1 → reconnected=1` 并恢复推流；服务器占用 CPU 5.6%/内存 8.5MB（空闲态快照）。
- 待办：控制台拉流端实现完成后，在 PC 侧先完成"网关 → ZLMediaKit → 控制台"跨进程联调（VM 与 Windows 可达性需验证）；断网恢复、端到端延迟需在联合场景实测，未测前不写数字。
- 板端 RTSP + MPP：待板子上线后复核（板子当前离线）。

## 7. 人脸注册、识别流水线与考勤状态机

### 7.1 识别流水线（已完成）

```
视频帧 → 单人脸跟踪（CSRT）→ 质量门控（SeetaQualityAssessor）
       → 特征匹配（FaceRecognizer）→ 连续 N 帧确认（AttendanceStateMachine）
       → 按人冷却 → SQLite 幂等写入 → 抓拍留证
```

| 规则 | 实现 | 测试 |
|---|---|---|
| 连续帧确认 | 默认 3 帧，可配置 1-10 | `AttendanceStateMachineTest` |
| 质量门控（识别） | 拦截亮度/尺寸/清晰度，容忍姿态告警 | `FaceQualityAssessorTest` |
| 质量门控（注册） | 四项全查 + 单人脸，拒绝多人和低质量照片 | `FaceQualityAssessorTest` |
| 按人员冷却 | 默认 30 秒，防重复识别 | `AttendanceRepositoryTest` |
| 手动签退确认 | 当前人员连续 3 秒正脸确认 | 手动流程（无自动化） |
| 未知人员 | 低于阈值显示"陌生人"，不写库 | 手动流程（无自动化） |

### 7.2 考勤状态机（已完成）

- 首次确认为签到；同一天再次确认且超过最小间隔（默认 4 小时）自动转为签退；已完成签退后重复确认抑制。
- 事件键 `number:日期:类型` 全局唯一，数据库唯一索引兜底。

### 7.3 注册流程（部分完成）

- 已完成：拍照 → 检测单人脸 → 脸图质量评估 → 注册特征 → 写入人员表（事务保护，失败回滚删除特征）。
- 待实现（非当前优先级）：人员暂停/停用标记、一人多模板、注册照片存本地照片库并统一路径管理。

### 8.3 事务与幂等（已完成）

## 9. 线程模型与可观测性（修订重点）

### 9.1 当前实际（4 线程，2026-09-12 线程重构后）

| 执行单元 | 现状 | 位置 |
|---|---|---|
| UI 线程 | 界面、事件处理、识别决策、只读查询 | `facerecognitionwin.cpp` |
| 视频源线程 | 视频源打开/轮询读取/关闭 | `videosourceworker.cpp` |

**历史风险（已消除）**：重构前 `OpenCV VideoCapture::read()` 和 SQLite 写入都在 UI 线程执行，真实 RTSP 网络抖动时会卡界面。

### 9.2 目标（线程重构已完成）

| 执行单元 | 目标职责 | 状态 |
|---|---|---|
| UI 线程 | 界面渲染、用户交互、结果显示 | 已完成（不再执行视频读取与数据库写入） |

### 12.2 面试追问准备（边界清晰）

- **流媒体的两个方向怎么讲？** 服务端/推流方向在网关（ZLMediaKit 多协议分发，PC 已验证）；客户端/拉流方向在控制台（RTSP 拉流解码 + 业务，实现进行中）。两个方向职责不重叠。
- **为什么客户端不用 OpenCV 直接拉流？** 本机 OpenCV 构建未启用 FFMPEG 后端；改用独立 ffmpeg 子进程解码，隔离进程崩溃，后续可平滑替换为直接 API。
- **为什么不让网关自己当 RTSP 服务器？** FFmpeg muxer 只能推流（`listen` 仅属 demuxer）；独立流媒体服务支持多客户端多协议，且与网关解耦。
- **为什么不用控制台自己做 RTSP 服务端？** 媒体服务端归网关，控制台只做业务层，分开讲清贡献。
- **为什么不用单帧匹配直接考勤？** 单帧模型波动大；连续帧确认影响误识率、属可调参数。
- **如何避免重复考勤？** 业务冷却 + 数据库唯一事件键双保险。
- **RTSP 断流后发生了什么？** 状态机进入断流等待并暂停识别；重连成功恢复读帧后才恢复识别；运行日志有时间线。
- **为什么用 SQLite？** 单机、写入简单、够用；适合本项目的演示与离线场景。
- **隐私边界？** 当前没有可控门禁；仓库只用虚构数据；项目定位为考勤记录工具。
