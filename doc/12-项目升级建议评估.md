# 对"嵌入式化改造建议"的独立评估

> 评估对象：一份主张"不新建项目、把 Qt 人脸考勤项目改造为 RK3568 嵌入式终端"的升级建议（用户提供）。
> 评估日期：2026-09-12。评估依据：本仓库真实代码、`doc/09` 网关交接记录、当日实测证据。
> 结论用途：决定是否采纳该方案，以及替代路线。
>
> **2026-09-12 晚补充**：对网关工作区的只读核查发现项目 1 已大幅推进（RTSP push 全功能、ZLMediaKit 阶段 1 PC 验证、73/73 测试），本文第 5 节路线 A 中"项目 1 收尾"的多项已完成；"流媒体两个方向"定位已并入 `doc/04` 第二轮修订。

---

## 0. 结论先行

| 层面 | 评价 |
|---|---|
| 战略出发点（不滥开新项目、追求两项目互补） | 有价值 |
| 方案对现状的描述 | 多处与真实代码不符 |
| 方案中的代码示例与 API | 存在虚构/无法对应的接口 |
| 方案前提（复用一个"成熟"的网关项目） | 前提不存在：网关 MPP/RTSP 尚未完成 |
| 工作量估计（2-3 周） | 严重低估，保守估计 1.5-3 个月 |
| 与已确立的架构分工 | 冲突：会造成两项目技术栈更深重叠 |
| **总体** | **方向启发有用，方案本身不可按条执行** |

---

## 1. 方案中成立的部分

1. "不推荐盲目开新项目、优先改进现有项目"——合理的工程原则。
2. 目标正确：两个项目应形成互补叙事，而不是各做各的。
3. 事实观察属实：项目 2（Windows+Qt）没有硬件加速、没有流媒体输出能力。
4. 若求职目标偏嵌入式/音视频岗位，项目 2 的平台匹配度确实弱于项目 1。

---

## 2. 事实性错误（附本项目证据）

### 2.1 "只是调用 FFmpeg API 解码"不属实

- 本项目代码没有直接调用任何 FFmpeg API（无 `avcodec_*`/`avformat_*`），实际使用 OpenCV `VideoCapture`。
- 更关键：本机 OpenCV 4.5.2 MinGW 构建经探测确认 `FFMPEG: NO`、`GStreamer: NO`（仅 DirectShow），连 `rtsp://` 都无法打开（2026-09-12 实测）。因此"项目 2 用 FFmpeg 软解码"这一前提在事实上不成立。
- 方案中"改造前代码"`avformat_open_input(..., av_find_input_format("dshow"), ...)` 在本项目中不存在。

### 2.2 代码示例与 API 虚构或无法对应

| 方案代码 | 问题 |
|---|---|
| `rkav::V4L2VideoCapture` / `#include "rkav/capture/v4l2_video_capture.h"` | 需核实项目 1 是否真有该命名空间与模块；无法核实前不能作为"直接复用"的依据 |
| `#include <ZLMediaKit/API.h>` | ZLMediaKit 没有该头文件 |
| `std::make_shared<RTSPClient>()->open(url, callback)` | ZLMediaKit 对外主要是 `mk_*` C API 与服务端组件，没有这种简单 C++ 拉流客户端 |
| `av_find_input_format("dshow")` | 项目 2 中不存在该代码 |

### 2.3 "复用第一个项目的成熟模块"——前提不存在

`doc/09` 记录的项目 1 当前状态：

- 网关源码停在"每帧输出包元数据"补丁的**未闭合语法错误分支**，尚未重新构建；
- 板端没有 554/8554 监听端口，RTSP 服务未验收；
- MPP H.264 编码仅官方样例验证过，网关自身输出未成功。

按该方案"复用网关模块"迁移项目 2，等于在未完成的地基上盖第二层。

### 2.4 指标缺乏依据

- "CPU 占用从软解码的 80% 降至 10% 以下"：无任何实测来源；且本项目实测瓶颈是 SeetaFace2 推理（`QueryTop` 单次约 400ms），H.264 解码并非主要开销。
- "49 项测试 + 120 小时长稳"（对项目 1 的宣称）：如用于面试，需能出示日志/报告证据，否则同属风险。

---

## 3. 策略性问题

### 3.1 与已确立的架构分工冲突

- `doc/04`（修订版方案）明确：**网关 = 媒体层（采集/编码/RTSP 服务），控制台 = 业务层（识别/考勤）**，两者的分工正是面试叙事的核心。
- 改造方案让控制台自己做 V4L2 采集 + MPP 解码 + 自行 RTSP 输出——与项目 1 职责重复。
- 方案自己批评"技术栈重叠"，而改造后重叠更深（两个项目都做 V4L2/MPP/RTSP）。

### 3.2 工作量严重低估

被低估的工作项：

1. SeetaFace2 及依赖的 aarch64 交叉编译与板端验证；
2. Qt 交叉编译（或去 GUI 后重做界面/服务化）；
3. MPP H.264 硬解码集成（而项目 1 连硬件**编码**都还没跑通）；
4. ZLMediaKit 交叉编译与集成；
5. 无 GUI 场景下的交互/运维重设计；
6. 全部回归与新增长稳验证。

且整体移植会推倒项目 2 已完成并验证的成果：14 项自动化测试、4 线程模型、质量门控、迁移框架、导入导出等。"2-3 周"不可信；保守估计 1.5-3 个月。

### 3.3 边界与授权

按 `doc/05` 协作边界与 2026-09-04 授权范围：当前授权是"修复 MPP H.264 编码并在原始 H.264 验证成功后实现只读 RTSP 输出"，**不包含在板端新建嵌入式人脸应用**。方案涉及的板端大规模新开发需要重新获取明确授权。

### 3.4 流程风险

该建议呈现典型的"看似合理"特征：虚构 API、拍脑袋的 CPU 数字、工作量表无数字却给出"2-3 周"结论。采纳前必须逐条技术验证。

---

## 4. 它真正击中的问题（可借鉴）

1. 项目 2 平台匹配度弱于项目 1（针对嵌入式岗位）；
2. 两个项目需要互补叙事，而不是独立孤岛；
3. "改进现有项目优于新建项目"的方向正确。

这些可以吸收，但解法不是整体移植。

---

## 5. 建议的替代路线

### 路线 A（推荐，低风险）

保持分工，把"两项目端到端联调"做成最强故事：

1. **项目 2 收尾**：RTSP 解码后端（方案 B 进行中，先解决本地回环源）、模块目录重组、指标扩展（P95/FPS）；
2. **项目 1 收尾**：MPP H.264 编码 + 只读 RTSP（既有授权范围内）；
3. **端到端联调**：网关 RTSP → 控制台识别 → 考勤落库。

叙事价值："我实现了嵌入式网关与桌面控制台的 RTSP 端到端链路"——这是两个项目各自单独都讲不出来的故事。真实产品（如安防/工业系统）就是"嵌入式设备 + PC 管理端"的异构组合，"平台不一致"不是减分项。

### 路线 B（可选，中风险，真实增加嵌入式含量）

不移植项目 2；待项目 1 的 RTSP 验收后，在板端增加一个**无 GUI 考勤代理**小扩展（复用状态机与 SQLite 逻辑，消费 RTSP 帧），工作量可控、证据真实、与项目 1 共用边界清晰。

### 路线 C（不推荐）

整体"嵌入式化"项目 2：与路线 A 目标重叠、重复项目 1 技术栈、成本高、丢弃已验证成果。

---

## 6. 对"改造后简历描述"的修正意见

不应写入（未实现或无证据）：

- "CPU 占用从 80% 降至 10% 以下"（无实测）；
- "集成 ZLMediaKit 实现识别结果推流 + REST API"（未实现，且在项目 2 中职责错位）；
- "支持运行时分辨率切换、零拷贝采集"（在未做前不写）。

可以保留（真实可验证）：

- 多源视频抽象（本地文件/摄像头已实测；RTSP 客户端状态机就绪、解码后端待引入）；
- 质量门控、连续帧确认、签到签退状态机、按人冷却；
- SQLite 幂等写入、迁移框架、快照留证、CSV 报表、人员导入导出；
- 14 项自动化测试、4 线程模型（UI/视频源/识别/存储）。

---

## 7. 当前 RTSP 方案 B 状态（暂停点）

- ffmpeg 已下载部署至 `D:\qtdeps\ffmpeg\bin\`（ffmpeg.exe / ffprobe.exe，各约 157MB），h264 解码、libx264 编码、rtsp 输入/输出均验证可用；
- 卡点：`-rtsp_flags listen` 的服务端命令未实际监听端口（netstat 无监听，日志显示被当作连接请求）；
- 下一步候选：调整 listen 参数写法重试；或引入 mediamtx（约 10MB）作为本地 RTSP 测试服务器；
- `RtspSource` 的 ffmpeg 子进程改造尚未开始编码。

## 10. 关于"Windows 平台不占优"的重新定位

- 若求职目标为嵌入式岗位，项目 2 的 Windows 平台匹配度确实弱于项目 1，这是客观事实；
- 但真实嵌入式产品普遍是"设备 + 上位机/管理端"的异构组合：项目 2 定位为"上位机控制台"是真实且合理的角色，不是硬伤；
- 真正的短板是：项目 2 缺少板端交付证据。补法有两条：路线 B 的小代理（真实嵌入式交付），或把项目 2 的工程能力（多线程、状态机、数据一致性、协议客户端）在话术上对齐嵌入式岗位需求；
- 忌两边都自称"嵌入式"却拿不出板端代码与证据——那才是减分项。
